## Initial snapshot: highest-risk findings and evidence limits

**Current disposition:** findings 1 (script identity), 2 (late headers) and 6 (aggregate storage) have verified follow-through below. Findings 4 (combined task trust/correlation) and 5 (combined Skills host contract) now have executable evidence recorded in the final disposition section. Finding 3 remains a host re-entry contract limitation, not an automatic-restart claim. References to resolved gaps in the initial checklist describe the original snapshot, not outstanding defects.

1. **Tasks script execution lacks recovery intent identity (source-determined gap).** `index.ts:1851` invokes `runMcpScript` without the outer Pi ID. Its inner `mcp-code.ts:206` call to `executeCall` omits the final `toolCallId` argument. `utils.ts:390` consequently supplies no ID; `proxy-modes.ts:1703` still supplies `conn.taskRecovery`; `mcp-tasks.ts:481` rejects before dispatch with “Recoverable Tasks require a stable Pi toolCallId”. The complete installation defaults to a recovery store. Thus configured task-session tools reached through normal `mcpScript` fail instead of executing. This affects an existing public route, not an invented feature. Acceptance needs real Pi script execution plus qualifying session expiry, one original invocation, distinct child intents for distinct inner calls. No runtime script reproduction was added in this read-only audit.
2. **Late-handle cancellation drops per-call wire headers (directly reproduced gap).** `PendingRawRequest` retains metadata but not dispatch headers (`mcp-tasks.ts:75`); `cancelLateTask` supplies only `Mcp-Name` (`:256`). A read-only Bun probe dispatched a tool with `context.headers.Authorization = "Bearer fake-per-call"`, aborted its local wait, then delivered its late task handle. Observed sends: `tools/call` had that header; `tasks/cancel` had only `{"Mcp-Name":"late"}`. Configured transport-level auth may still be injected, so this is specifically lost per-request context, not a claim that all cancellation is unauthenticated. SDK recovery guidance explicitly preserves wire context. Add a strict real-HTTP late-handle fixture requiring the per-call header; retain SDK framing and normal transport authentication.
3. **Durable recovery is available on re-entry, not automatically rediscovered as unattended work.** `FileTaskRecoveryStore` exposes read-by-toolCallId/CAS, not enumeration; `callToolViaTaskSession` resumes when the same intent is re-entered. Actual Pi expiry recovery and reopened-store/input replay are covered. No startup scan automatically schedules all outstanding intents. T2's durable-ID SHOULD is implemented by persistence plus explicit resumption, but a claim of automatic post-process-restart continuation is not proven. Coordinator must state the normal host re-entry/recovery contract, not promise remote exactly-once effects or blind retries of intent-only records.
4. **Combined trust/correlation evidence remains narrower than source support.** Production modern elicitation acceptance/replay is covered, standalone sampling approval/denial is covered, and legacy receiver-side task sampling is covered. Those do not substitute for a real task-backed tool requesting approved/declined sampling, nor for interleaved legacy tool tasks requesting correlated server-to-client inputs. These are missing combined regressions, not demonstrated permission bypasses.
5. **Skills exact-origin/collision/nesting behavior has substantial implementation but incomplete dedicated host evidence.** Same-URI/different-server reads are covered; URI-based selection retains duplicate names. A single actual-host scenario combining local/remote same-name skills, two remote equal names, a nested `SKILL.md` supporting read and separately denied nested activation was not found. Do not describe this as a demonstrated collision or consent defect.
6. **Recovery storage has no aggregate admission bound in the inspected snapshot.** Rows retain intents, references, input decisions and results indefinitely. This is a local resource-management implementation gap, not a Tasks wire MUST, and requires an explicit retention/admission policy. Do not delete uncertain intents to make space or turn retention into an invented remote-expiry retry policy.

These are bounded implementations, not full-protocol acceptance. Skills source and its initial evidence mapping were not changed by this follow-through.

| Finding 6 / bounded storage | Initial budget tests admitted every competing process and allowed a new effect despite a full budget. A review then reproduced the initial reservation flaw: tiny completed calls exhausted the default byte budget at 64 lifetime calls. | `FileTaskRecoveryStore(scope, { directory?, maxRows?, maxBytes?, maxRecordBytes? })` supports one shared private database keyed by actual session/tool-call IDs. Admission/CAS/accounting use BEGIN IMMEDIATE. Active and uncertain records reserve maxRecordBytes; completed records release only unused capacity and retain immutable full intent/result/input ledger at actual encoded byte charge including identity keys, minimum 512 bytes. No GC, expiry or uncertain-intent retry. A record reservation below the accounting floor is rejected. Nine budget tests include separate six-process row and byte contention, live rollback-journal measurement, retained legacy unknown rows, updates at capacity, and 70 tiny completed calls followed by an explicit configured row-limit rejection. |

Defaults remain **1,024 retained lifetime rows**, **64 MiB aggregate reservation**, **1 MiB maximum record reservation**. The byte budget can support at most 64 simultaneous full active/unknown reservations, less space retained for completed records; it is **not a 64-total-calls cap**. Terminal results/input ledgers larger than their reserved record capacity fail closed while preserving prior durable state. Row exhaustion still rejects new intents; retained records are never automatically removed.

Physical allowance remains bounded separately from logical charges: SQLite database capped by max_page_count at `floor((2*maxBytes + 8192*maxRows + 65536)/pageSize)*pageSize`; rollback-journal allowance `2*databaseLimit + 65536`. Default allowances are approximately 136 MiB database and 272 MiB rollback scratch, not measured steady-state usage. DELETE journal, no WAL or disk temp tables. Logical reservation is not a promise of disk availability against unrelated writers or hardware failures. Main owns default-global-directory wiring; omission of directory retains the per-session path for custom factories/tests.

## Protocol eras: do not combine incompatible obligations

| Concern | T1: 2025-11-25 | T2/TD: modern current |
| --- | --- | --- |
| Negotiation | Initialize `tasks` request-category capabilities; tool `execution.taskSupport` | `server/discover` extension; extension capability on every request |
| Creation | Caller sends `task: {ttl?}`; required/optional/forbidden tool semantics | Server chooses immediate vs `resultType: "task"`; no caller task preference |
| Handle | `{task:{...ttl,pollInterval}}` | Flat task with `ttlMs`, `pollIntervalMs` |
| Results | `tasks/get` status, `tasks/result` final result | Terminal result/error inline in `tasks/get` |
| Input | Correlated peer requests, `related-task`; preemptive `tasks/result` on input-required | `inputRequests` keyed on task; responses through `tasks/update` |
| Inventory | `tasks/list`, opaque cursor pagination | No wire `tasks/list`; SDK local inventory is not remote discovery |
| Cancellation | Server transitions to cancelled before acknowledgement | Cooperative acknowledgement; may remain working or complete normally |
| Tool `isError` | Can be task status failed, with original tool result from `tasks/result` | Completed status with `isError` result; failed reserved for JSON-RPC errors |
| Notifications | Optional `notifications/tasks/status`; must not rely on them | Optional `subscriptions/listen` taskIds / `notifications/tasks` |

The public `mcp_protocol` action named `tasks/result` is an SDK outcome abstraction on modern sessions; it must not imply a modern wire `tasks/result`. The modern no-list rejection in `runtime-protocol.ts:383` is correct.
